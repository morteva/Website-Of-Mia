# Morteva payment connection

The Worker integrates with a replaceable PayRam server. Browser bags contain only product IDs and quantities. The Worker reads the checked-in catalog, validates availability, computes USD cents, stores an immutable order snapshot in the dedicated SHOP_ORDERS D1 database, and creates a USDC/Base payment with the order ID as invoiceID. No shop records are written into the shared CMS database.

Set Worker secrets PAYRAM_BASE_URL (HTTPS origin only), PAYRAM_API_KEY and PAYRAM_GATEWAY_KEY. The gateway key authorizes server calls through the local public proxy; only an allowlist of customer checkout routes is exposed without it. Public requests have authentication cookies and Authorization stripped. The admin interface stays on localhost port 8089. Set SHOP_CHECKOUT_ENABLED=true only after the mainnet wallet, consolidation and public checkout have been verified. Without these, checkout remains disabled. API keys must never appear in public assets or Git.

Register https://morteva.com/api/shop/webhook in PayRam. The Worker requires X-Payram-Signature HMAC authentication and verifies the payment's reference, invoice, USD amount and actual state against the authenticated PayRam API. It does not trust webhook status claims alone. Paid orders cannot be downgraded by a delayed event. Customer payment checks also reconcile the authenticated API, allowing recovery from missed webhooks.

PayRam 3.9 closes an invoice after its first deposit even when underpaid. A later deposit to the same customer address becomes a separate system invoice. The Worker credits that additional payment only after authenticated API checks match the original order's unique customer ID, project, Base network, token and deposit address, and the additional deposit has its required confirmations. The dedicated payment-credit table counts each reference once using exact millionths of a dollar. The original provider invoice may remain PARTIALLY_FILLED while the shop order becomes paid from the verified combined deposits. Apply both shop migrations before releasing this version. Missing additional webhooks need a signed replay of the real additional reference; checking the original reference alone cannot discover them. Customer messaging tells underpaid customers to contact Morteva before sending more.

The live Base test received 0.00004 ETH and automatically collected 0.000039 ETH into the configured receiving wallet, with 0.000001 ETH recorded as the configured operator fee. Deployment and collection also consume gas from the separate payment-fee wallet. This observation establishes collection routing, not a promise of fee-free payments. Small native-ETH quotes can round below an invoice total; the storefront creates Base USDC checkouts by default.

Checkout request IDs prevent a double click or retry from creating another payment. Ambiguous creation failures enter REVIEW rather than issuing a second invoice. Resolve those against PayRam before retrying. Public order status requires the random order ID and exposes only payment state and total, not email or line items. Each client is limited to 20 new orders per hour, using a one-way keyed IP hash. Order emails and snapshots are private D1 runtime data, not Git source.

Apply migrations with wrangler d1 migrations apply SHOP_ORDERS --remote. Preserve both the orders database and PayRam's PostgreSQL data/AES key across updates. A mainnet PayRam instance must use a different data directory and encryption key from the test instance. The local test deployment at port 8088 remains separate from mainnet at port 8089.

The catalog stays empty until the owner adds actual products. Open `/wmm4?section=shop`, choose Add item, enter the name, description and USD price, then Save draft or Publish items. Photos use the existing media uploader. Shipped items require shipping per item and allowed country codes. Tax is an owner-entered percentage, not automatic jurisdiction determination. Availability is a switch, not a stock reservation system. Hide and Trash are reversible and take public effect after publication.

Shop publishing uses the existing authenticated CMS and GitHub synchronization: visible products are exported to `public/shop-catalog.json`, with a baseline in `public/cms-published/shop.json`. Private drafts and trashed content remain in D1. The export refuses to overwrite a catalog modified in the Site Editor after the baseline. Apply migration `0003_fulfillment.sql` before deploying the storefront changes. Preserve the existing NEWSLETTER service and the shared `mira-site-media` R2 bucket binding.

Open `/wmm4?section=orders` to see customer orders, shipping addresses and verified payment states. Save delivery status, tracking links, customer-facing delivery notes and private notes there. An unpaid order cannot be marked fulfilled. Refunds are handled manually through the payment provider; these controls do not issue refunds or send email. Customer receipts use the random order ID as a private bearer link and disclose payment/delivery state only. Buyer addresses, email and private notes stay behind the owner login.

For digital items, upload a paid delivery file before publishing. R2 marks these files private; ordinary `/cms-media` access denies them even if a media record is accidentally marked public. Download routes require a paid order containing that item's immutable file snapshot. Receipts offer the download after payment verification. Keep the receipt link private. Card availability is controlled by PayRam's live payment options and underlying provider eligibility; test crypto payment success does not establish card acceptance or privacy in disputes.

Release through the existing GitHub main and guarded deployment workflow. Keep NEWSLETTER and all existing site routes intact.
